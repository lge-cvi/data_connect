1-1. 기본교육 MVP의 한계

기본교육에서 만든 대시보드는 숫자가 화면 코드 안에 직접 들어 있습니다. 데이터가 바뀌어도 화면은 바뀌지 않습니다.

고정형: 데이터가 코드에 포함된 화면 (기본교육 MVP)

// Copilot이 CSV를 읽고 // 숫자를 그대로 써 넣음 const DATA = { kpi: { total: 1000, nps: 39.8 }, by_product: [ { name: "휘센 에어컨", nps: -32.9 }, … ] };

연동형: 열 때마다 조회하는 화면 (이번 과정)

🧱MVP 방식의 한계 4가지

① 용량

10만 행 파일은 AI 대화창에 모두 들어가지 않음. 일부만 반영돼도 알아채기 어려움.

② 최신성

데이터가 바뀔 때마다 다시 첨부해 새로 만들어야 함. 주 1회면 연 52회.

③ 보안

고객명·연락처가 섞인 원본을 외부 AI에 올릴 수 없음.

④ 공유

파일을 메일로 돌리면 누가 최신본을 보고 있는지 알 수 없음.

해결 방향: 데이터를 AI나 화면 코드에 넣지 않고, 데이터는 저장소에 두고 백엔드가 필요할 때 조회하도록 구성합니다.

🔌API의 개념

API(Application Programming Interface)는 한 프로그램이 다른 프로그램에게 데이터를 달라고(또는 저장해 달라고) 요청하는 정해진 방식입니다. 프로그램이 정해진 주소로 요청을 보내면 정해진 형식(주로 JSON)으로 결과가 돌아옵니다.

📜

명세로 정의된다

요청 주소, 조건, 응답 형식을 명세서로 정해 둡니다. 상대 시스템의 내부 구조를 몰라도 명세대로 호출하면 됩니다.

📂

제공된 범위만 조회한다

상대 시스템의 DB에 직접 접속하지 않고 제공된 API로만 요청합니다. 제공 범위는 API를 만든 쪽이 정합니다.

🔑

인증이 필요하다

요청할 때 API 키나 토큰으로 인증합니다. 권한 범위 안에서만 응답하며, 호출 횟수도 제한할 수 있습니다.

🗄DB to DB 연동의 개념

  
원천 시스템의 DB에서 우리가 쓸 분석용 DB(데이터 마트)로 정해진 주기에 데이터를 복사하는 방식입니다. 복사한 뒤에는 원천 시스템을 다시 조회하지 않고 분석용 DB에서 SQL로 집계합니다. 2교시의 EAP → BigQuery가 이 방식입니다.

전체 적재 vs 변경분 적재
매번 전부 다시 옮기거나(전체), 바뀐 것만 옮깁니다(변경분·증분). 데이터가 많으면 변경분 적재를 사용합니다.

    
배치 스케줄

전용 계정 · 접속 경로
적재용 계정과 조회용 계정을 나누고, 허용된 경로로만 접속합니다.

  


  
🧭데이터 저장소 용어: DB · DL · DW · DM

  
DB to DB로 데이터를 옮기다 보면 저장소 이름이 여러 개 나옵니다. 데이터가 어디서 만들어지고, 어디에 모이고, 어디서 꺼내 쓰는지에 따라 이름이 다릅니다.

  

    🏢 업무 DB→🌊 DL→🏭 DW→🛒 DM→📊 대시보드
  

  

    

      
DBDatabase · 데이터베이스

      
업무 시스템이 매일 쓰고 고치는 저장소

      
접수·처리·결제처럼 한 건씩 빠르게 기록하는 데 맞춰져 있습니다.

      
예 SMILE, GSFS, GSCS 등 업무 시스템의 데이터 저장소

      
여기에 분석 쿼리를 직접 돌리면 업무 시스템이 느려질 수 있습니다.

    

    

      
DLData Lake · 데이터 레이크

      
여러 시스템의 데이터를 원본 그대로 모아 두는 호수

      
표뿐 아니라 로그·파일까지 가공 없이 쌓아 두고, 필요할 때 꺼내 씁니다.

      
예 EDL, DDL 등

      
정리 전 상태라 바로 대시보드에 쓰기는 어렵습니다.

    

    

      
DWData Warehouse · 데이터 웨어하우스

      
정리해서 같은 기준으로 맞춘 전사 분석 창고

      
코드·날짜·단위를 통일하고 여러 시스템 데이터를 합쳐 이력을 오래 보관합니다.

      
예 EDW, NEDW 등

      
범위가 넓어 내 업무에 필요한 것을 찾는 데 시간이 걸립니다.

    

    

      
DMData Mart · 데이터 마트

      
DW에서 한 부서·주제에 필요한 것만 꺼내 둔 매장

      
컬럼과 기간을 좁혀 두어 조회가 빠르고 비용이 적게 듭니다.

      
예 대시보드가 참조하는 엑셀 파일 등

      
대시보드가 직접 조회하는 곳은 대부분 이 단계입니다.

    

  

  
이 과정에서는 EAP가 원천 데이터를 BigQuery에 적재하고, 승인된 범위를 내 사번 데이터셋의 뷰로 제공합니다. 대시보드 입장에서는 이 뷰를 마트(DM)처럼 조회한다고 이해하면 됩니다.

2-2. GCP · BigQuery 기본 개념

  
GCP는 구글의 클라우드, BigQuery는 그 안의 대용량 집계 전용 데이터베이스입니다. 구조를 엑셀에 대응하면 다음과 같습니다.


  

    

      
📁 프로젝트 = 회사 공유 드라이브 · 예: pjt-lge-edl-user

      

        
📗 데이터셋 = 엑셀 파일 · 예: ZU_사번 (EAP가 본인 이름으로 만들어 줌)

        

          
📄 테이블 · 👁 뷰 = 시트 · 예: FV_edl__L0_SMIP__SI_VOC

        

      

    

    

      이름(ID) 읽는 법
      
pjt-lge-edl-user . ZU_사번 . FV_edl__L0_SMIP__SI_VOC
  프로젝트            데이터셋     뷰

      
코드와 SQL에는 세 부분을 모두 씁니다. 프로젝트 이름에 하이픈(-)이 있어 SQL에서는 전체를 백틱(`)으로 감쌉니다. DBeaver 탐색기에서 프로젝트 › 데이터셋 › 뷰 순서로 보입니다.

    

  


  
👁테이블과 뷰

  

    
📄 테이블
데이터가 실제로 저장된 곳. 원본 테이블은 EAP가 관리합니다.

    
➜

    
👁 뷰 (View)
원본 테이블을 조회하는 저장된 쿼리. 데이터를 복사하지 않고, 승인된 범위만 내 데이터셋에서 보이게 합니다.

  

  
조회 방법은 테이블과 같습니다(SELECT … FROM 뷰이름). 뷰를 조회하면 원본 테이블을 읽으므로 비용 원칙(필요한 컬럼만 조회)도 동일하게 적용됩니다.


  
⚡BigQuery의 특징

  

    
집계에 특화
수억 행의 합계·평균도 수 초 내 처리. 행 단위 수정이 잦은 업무에는 맞지 않습니다.

    
읽은 양만큼 과금
쿼리가 스캔한 바이트 기준. 필요한 컬럼만 선택하면 비용이 줄어듭니다. SELECT *는 사용하지 않습니다.

    
세분화된 권한
프로젝트·데이터셋·테이블 단위로 읽기·쓰기·실행 권한을 나눠 부여합니다.

2-3. 서비스 계정과 키

  
백엔드는 프로그램이므로 사람 계정 대신 프로그램 전용 계정(서비스 계정)으로 인증합니다. 이때 사용하는 인증 파일이 키 파일(JSON)입니다.


  

    
👤 사람 계정
내 사번 계정. EAP·사내 시스템에 로그인해서 데이터를 요청하고 키를 내려받을 때 사용.

    
🤖 서비스 계정 + 키 파일
EAP에서 내려받은 키 파일. DBeaver·백엔드 코드 같은 프로그램이 이 파일로 BigQuery에 로그인합니다. 파일만으로 로그인할 수 있으므로 비밀번호와 같이 관리해야 합니다.

  


  
🔍키 파일(JSON) 구성

  

    
"type"service_account: 서비스 계정 키

    
"project_id"키가 속한 프로젝트

    
"client_email"서비스 계정 주소 (권한 부여 대상)

    
"private_key_id"키 번호: 폐기할 키를 식별할 때 사용

    
"private_key"비밀키 본문. 화면·메일·메신저·Copilot에 붙여넣지 않습니다

✅ 대시보드에 쓰는 6개

      P_PTT 파티션 날짜(=접수일) · 기간 조건은 이 컬럼으로

      ETL_LOAD_TS 배치 적재 시각 (UTC 저장)

- ETL_LOAD_TS(TIMESTAMP): EAP 배치 적재 시각, UTC로 저장됨
- VOC_NO(STRING): VOC 번호. 같은 번호가 2행 이상인 경우가 있음
- VOC_STATUS_NAME, LARGE_CLASS_DESC, TGET_DEPT_NAME(STRING): 진행상태, 대분류, 대상 부서 이름

[화면에 필요한 데이터]
화면은 GET /api/voc?from=YYYY-MM-DD&to=YYYY-MM-DD 로 아래 값을 받아.
- kpi: VOC 건수(고유 VOC 번호 기준), 최신 접수일, 마지막 배치 적재 시각(한국시간)
- by_week: 주별(월요일 시작) 건수
- by_large, by_status, by_dept: 건수 상위 8개

[데이터 특성과 제약]
- EAP는 하루 한 번 새벽에 배치로 적재돼서, 결과는 1시간 캐시해도 돼
- 기간 조건은 파티션 컬럼 P_PTT 로 걸어야 스캔량이 줄어들어. 조건 값은 쿼리 파라미터로 넘겨 줘
- ..._DESC, ..._DETAIL 같은 자유서술 컬럼에는 개인정보가 섞일 수 있어서 조회하면 안 돼. 위 6개 외의 컬럼은 쓰지 말아 줘
- 키 경로는 .env 의 GCP_KEY_PATH 에 있고, 키 내용·경로가 응답에 나오면 안 돼
- maximum_bytes_billed 로 스캔 상한을 두고, 응답 meta 에 조회 시각·캐시 여부·스캔 바이트를 넣어 줘
- 서버는 내 PC(127.0.0.1)에서만 열고, 대시보드 화면 외의 파일은 내보내지 않아야 해 (.env·키 노출 방지)
- 오류가 나면 화면에는 짧은 안내만, 자세한 내용은 터미널에 남겨 줘

[결과물]
